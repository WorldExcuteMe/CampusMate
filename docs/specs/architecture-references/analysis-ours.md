# CampusMate backend agent architecture — audit

**Scope.** `backend/src` (Node 24 type-stripping, zero-dep core) is **14,882 non-test lines + 9,427 test lines / 104 test files** — the "~6000-line" framing understates it ~2.5×; upgrade sketches stay 2–5 files each.

## 1. Current architecture

A single-process product agent; the HTTP layer never runs the agent. `POST /v1/tasks` validates owner/budget/provider, writes a `queued` Task (+ session turn, deduped by input hash, one in-flight turn per session) and returns. A polling Worker claims with a 60s lease + 15s heartbeat, replays the latest checkpoint (messages, transcript, repeat counts, tool errors), builds a layered context (stable system prompt, always-injected task-state "fact source", profile, session summary, turn-group-packed history), gates tools through an ability manifest, then runs a bounded loop (20 rounds, 60 when toolCalls budget ≥80): one `transport.chat` per round (native tool calls with strict-JSON text fallback), sequential tool execution through an idempotency/approval/timeout wrapper, observation insert, checkpoint. A 4-D budget (tokens/toolCalls/wall-clock/USD) hard-stops with partial work preserved. An independent Evaluator then re-fetches evidence URLs, appends runtime/document/business checks, and only a passing certificate yields `succeeded`; otherwise `failed`/`paused`/`needs_input`, resumable by checkpoint replay. Proposal intents bypass the loop into a staged document pipeline with one verify/revise pass.

**Flow:** `POST /v1/tasks` (`api/server.ts:179`) → `createSessionTask` (`runtime/store.ts:88`) → `Worker.claimNext`+heartbeat (`runtime/worker.ts:153`) → prepare: checkpoint replay, session history+summary, manifest (`worker.ts:204-355`) → `buildContext` (`core/context-builder.ts:23`) → `runAgentLoop`: chat (`core/llm.ts:72`) → tool call → `wrappedExecuteTool` (idempotency+approval+timeout, `worker.ts:274`) → observation → `trimToBudget` → checkpoint (`core/agent-loop.ts:491-815`) → `Evaluator` (`core/evaluator.ts:54`, `worker.ts:479`) → status → SSE `server.ts:254` → `/resume` (`server.ts:285`) replays unfinished calls (`agent-loop.ts:455-490`).

## 3. Top 10 gaps, ranked by expected benchmark impact

1. **Serial tool execution.** `READ_PARALLEL` (`agent-loop.ts:83`) is dead; calls await sequentially (`:698-717`, resume `:472-490`). Missing: `allSettled` batching of read-only tools with per-call budget/timeout and one checkpoint per batch. A 4-URL turn costs 4× RTT and 4 rounds' worth of budget.
2. **No plan/todo ledger.** `planner.ts` is complete but `nextReadyStep` is unreferenced, `planGoal` only feeds `workflows.ts:94`, and the checkpoint hardcodes `stepProgress: {}` (`agent-loop.ts:394`) while `taskContextSummary(task, [])` (`worker.ts:350`) always reports zero steps. Missing: plan tool + ledger in `CheckpointState` + step-scoped acceptance.
3. **Evaluator verdict never re-enters the loop.** Certificate is computed after return and only sets status (`worker.ts:479-493`); `RecoveryEngine`'s evaluation→`reexecute` policy (`recovery.ts:30,57`) is imported only by tests; the only repair loop is in the document pipeline (`proposal.ts:68-82`). Missing: bounded repair turn fed by failed criteria.
4. **Compaction is extraction, not summarization.** `summarizeDropped` keeps 160 chars/message (`context.ts:108-115`), dropping IDs, user corrections and decisions, and rewrites the prefix each time. Missing: model compaction with anchored-facts block. Hits `conversation-long`, `long-horizon`, `stress-context`.
5. **Trimming corrupts structure and advertises a phantom tool.** `truncateTool` cuts head 4096/tail 1024 chars (`context.ts:61-71`) → invalid JSON; notice recommends `rag_search`, which has no definition (only `capability.ts:59`, `tool-registry.ts:28`). Missing: JSON-aware per-tool renderers / real retrieval.
6. **Memory never learns.** `addEpisodic`/`addProcedural` have no production callers; retrieval prints `type#seq` and skill names (`context-builder.ts:40-41`). Missing: post-task write-back + relevance-ranked retrieval. Hits `memory-isolation`.
7. **Skills absent from the cloud loop.** `skill_open` exists only in the local runtime (`local-app.ts:50`), dumps whole instructions, and repo `skills/*/SKILL.md` are never read. Missing: runtime-agnostic catalog with progressive disclosure.
8. **No steering, no delegation.** Interruption is one-way cancel (`server.ts:281`, `worker.ts:185-190`); corrections require a new task; zero MCP/subagent references. Missing: mid-run inbox injection and a child-agent primitive.
9. **Prompt-cache policy idle by default.** 455-line tracer observes reuse, but tail-stable merge/effort lock need `CM_PREFIX_POLICY=1` (`llm.ts:54,115-150`); compaction guarantees periodic invalidation; hit-rate never aggregated.
10. **Telemetry last-write-wins, dead metrics, duplicated approval authority.** `worker.ts:462` overwrites `lastRequest` per round; `MetricsCollector` unused; `toolRequiresApproval` (`tool-registry.ts:59`) is never called while `approval.ts:57` decides. Indirect but blocks tuning routing/caching and risks drift.

## 4. Three realistic upgrade candidates

**A. Parallel read-only tool batches (~150–200 LOC).** In the native-call branch (`agent-loop.ts:693-724`), partition calls into `READ_PARALLEL` vs ordered, run reads with bounded concurrency (`allSettled`, say 4) under existing per-tool timeouts, append observations in call order, run repeat/progress tracking once, budget-check before each dispatch, write one checkpoint per batch. Files: `core/agent-loop.ts`, `core/agent-loop.test.ts` (ordering, uncertainty, single CP). Low risk; preserves transcript order.

**B. Durable plan ledger + step-scoped execution (~500 LOC).** Wire `planner.ts` into the loop: steps with acceptance in `CheckpointState.stepProgress`, a `plan_write`/`plan_update` tool validated by `validateDag`, compact ledger injected into the task-state layer, step status from observations, incomplete steps routed into the existing nudge path instead of regex streaks; reuse `proposal.ts`'s per-step checkpoint pattern. Files: `core/planner.ts`, `core/agent-loop.ts`, `runtime/worker.ts` (+`taskContextSummary`), `core/context-builder.ts`, `runtime/workspace-tools.ts`, tests `planner.test.ts`, `agent-loop.test.ts`, `worker-session.test.ts`.

**C. Verification→repair turn (~250–350 LOC).** On certificate failure over repairable criteria (missing artifact/deliverable, unverified evidence), re-enter the loop once with failed criteria + current artifacts as a system message, `maxRounds`≈6, tools narrowed to the failing subsystem, braked by `RecoveryEngine`'s `reexecute` counter; mirror `proposal.ts:68-82` and reuse the post-loop doc/business checks. Files: `runtime/worker.ts`, `core/evaluator.ts` (classify repairable), `core/recovery.ts` (wire), `core/agent-loop.ts`, tests `worker-evaluator.test.ts`, `evaluation/checks.ts`. Highest pass@1 per LOC, but spend tokens — gate on budget headroom.
