# Agent v2 方向取舍与验证方案（CampusMate）

> 依据项目初衷做范围裁剪：CampusMate 是**面向中国大学生的本地优先 AI 助理**——文件/文档/课表/日程/
> 群通知/公开信息核验/本机工作区工具，强调真实交付物、本机隐私、可控审批、可恢复、可解释。
> 它不是通用 CLI coding agent，也不是研究型多代理系统。本文件给出"保留什么、砍掉什么、怎么验证"。

## 1. 取舍原则

1. **只做学生高频、结果可交付、失败可恢复的场景**；不为炫技增加机制。
2. 每个新机制必须能通过 golden 回归或体验流证明收益，否则回退（单变量、可开关）。
3. 拒绝引入第二状态模型（如 LangGraph/多代理框架的状态机）与重型运行时；以现有
   `CheckpointState` + 事件日志为唯一事实来源。

## 2. 保留（v2 核心，已落地或进行中）

| 能力 | 状态 |
| --- | --- |
| 事件溯源会话日志（append-only + 投影 + 重放/修复 + 持久化脱敏） | 已落地（P0/P2a） |
| 上下文工程：结构化压缩、JSON-safe spill、计划持久化、技能渐进披露、稳定前缀 | 已落地 |
| 工具契约：schema/参数校验/结果信封/错误可纠正/并行只读/审批/幂等/重试 | 已落地 |
| 验证收敛：独立 Evaluator + 有界修复轮 | 已落地 |
| 可观测：逐请求 telemetry、run.summary、前缀指纹、成本字段 | 已落地基础 |
| 模型档位（auto/max 等）与成本预算 | 已落地 |
| 轻量记忆（episodic/procedural 任务后写入 + 检索） | P1/P2 |
| golden 回归集 + 体验 E2E | P1（本文件第 4 节） |

## 3. 砍掉/搁置（及理由）

| 砍掉项 | 理由 | 重新考虑的触发条件 |
| --- | --- | --- |
| **PTC / code mode**（程序化工具调用、代码沙箱一次编排多工具） | 沙箱 + 代码面复杂度高；学生任务用现有工具/workspace_run 已可完成；收益未证明 | 出现"单任务需 20+ 次工具编排"的真实需求 |
| **computer use / 屏幕自动化** | 不可靠、安全风险高；已有受控 `campus_browser` 读授权网页 | 校园系统必须点按操作且无 API/导出 |
| **多代理团队 / workflow / A2A** | 约 15× token 成本，学生任务并行度低 | 明确出现可并行的多子任务批量场景 |
| **通用子代理** | 只保留两个受限场景（研究汇总、独立验证），不做通用 delegation | 上述场景验证有效后再扩展 |
| **自进化流水线 / ToT / MCTS / 反思树** | 收益不确定、成本高 | 有稳定 eval + 人工评审流程后再实验 |
| **重型向量记忆基础设施（Mem0/Zep 独立服务）** | 学生规模数据用 Postgres/文件 + 关键词/可选 embedding 足够 | 记忆规模 >10 万条且召回明显不足 |
| **MCP 作为核心路线** | 降级为"可选连接器"，暂不进入核心重构 | 需要接入第三方/校园系统工具时 |
| **多模态实时音视频/语音** | 非核心场景 | 产品明确要求 |

## 4. 新 agent 怎么测（五层，从机制到真实体验）

### L1 单元/集成测试（已有 680 项）
机制正确性：事件投影/修复、压缩、计划、并行读、修复轮、工具协议、审批、预算、恢复。CI 必跑。

### L2 golden 回归集（P1 交付，CI 闸门）
- **20–30 条"产品旅程"**，离线确定性：in-memory store + mock transport + fake tools，不消耗模型用量；
- 覆盖：文档生成并导出、群通知整理、课表导入预览、待办/提醒、工作区文件处理、公开信息核验、
  审批暂停→批准→继续、预算不足→加预算→继续、服务重启→恢复、取消/超时/重试、安全边界（SSRF/审批绕过）、
  记忆写入与召回、计划中断后 resume；
- 断言：任务终态、验收证书、交付物真实存在、事件序列（turn/tool/plan/repair）、用户可见回复要点；
- 每次架构变更必须跑；**L2 通过率 ≥90% 且无稳定性 flake** 才允许合入高风险改动。

### L3 体验流 E2E（真实浏览器，Playwright）
5 条真实用户流（真实页面 + 真实本地服务）：
1. 登录 → 发"整理这周的群通知" → 工具执行 → 结果卡 → 历史回看；
2. 发"生成周报并导出 docx" → document_create/inspect/export → 下载文件；
3. 触发需审批的本地文件写入 → 审批弹窗 → 批准 → 继续 → 完成；
4. 任务中途断网/重启服务 → 任务 paused/恢复 → 续跑成功；
5. 预算不足暂停 → 增加预算 → resume → 完成。
- 指标：首响时延、完成时延、轮次/工具数、暂停/恢复成功率、错误提示可读性、控制台无报错。

### L4 轨迹质量复盘（数据驱动）
从事件日志 + run.summary 导出：计划使用率、并行批次数、修复轮触发/成功、工具错误分类、
压缩次数与保留项、token/cache/成本；每周抽 10 条轨迹人工读，形成"体验问题清单"。
**是否"管用"以这里 + L2/L3 为准，不以榜单为准。**

### L5 小规模真实使用（dogfood）
3–5 个真实同学场景（课表、周报、通知、材料整理），记录卡点与体感；不做刷榜。
发现问题回灌为 L2 golden 用例。

## 5. Go / No-Go 标准

- L1 全绿；L2 ≥90% 稳定通过；L3 五条流 100% 可走通且无严重缺陷；L4 核心指标不退化；
  L5 无阻断性问题 → 进入发布候选。
- 任一新机制在 L2/L4 无改善 → 回退对应机制（保持开关可关）。

## 6. 后续基准策略

不再全量刷 Terminal-Bench 等榜单；只保留 AppWorld/OfficeBench/GDPval 的失败集小样本（每轮 3–5 题）
作为端到端对照，主证据来自 L2 golden 与 L3 体验流。

## 7. 通用测试集策略（保留，但收紧为"能力抽样"）

结论：**保留通用测试集，但只作为外部效度抽样与能力 canary，不再是优化目标，也不刷榜。**

- 定位：防止 golden 回归过拟合我们的 mock/产品路径；用外部真实题面验证"换了场景还管用"。
- 抽样规则：固定清单、固定种子、小样本（每轮 3–10 题）、相邻时段做 baseline/candidate 对照；
  只用官方 verifier 出证据（CTRF/原始日志），环境受阻题单列。
- 保留的集合：
  1. **AppWorld / OfficeBench / GDPval 失败集**：每轮挑 3–5 题（文档/多步工具/研究写作）；
  2. **Terminal-Bench 代码任务 canary**：挑 8–10 题有代表性的代码任务（构建、调试、脚本、数据处理），
     官方 verifier 计分——这也是 coding 能力的端到端外部检验；
  3. 真实校园网站授权样本（手动核对结果，不进 CI 计分）。
- 不再使用：GAIA（需授权）、τ-bench 实时（模拟器依赖）、WebArena（本机环境）、全量 Terminal 89 题。
- 通过口径：canary 集"相对基线不退化 + 关键失败类型减少"即可，不与公开榜单横向比较。

## 8. Coding 能力增强路线（保留并强化）

判断：**在"从复杂高校网站/系统获取信息"这类任务里，coding 不是可选项，而是通用解法**——
JS 渲染、登录态、分页、反爬、非结构化页面解析、批量校验，最后都要落到"写代码 + 长任务执行 + 自检"。
因此 coding 能力作为 v2 的一等能力保留并增强（但 PTC/code-mode 运行时不引入，保持 code-as-tool）。

能力阶梯（用于设计工具、技能与评测）：

| 级别 | 能力 | 现状/计划 |
| --- | --- | --- |
| C1 | 文件读写、脚本编写与执行、产物回读 | 已有（workspace_* + 自检指令） |
| C2 | 依赖安装、HTTP/JSON/HTML/PDF 解析、错误可恢复 | 增强：workspace_run 依赖安装白名单 + 更长超时 + 解析技能 |
| C3 | 浏览器脚本化：代码生成 Playwright 脚本，受控本地 Chrome 读取授权页面（登录态） | 计划：代码与 browser 混合工具；网络域名白名单 |
| C4 | 长任务：多站点批处理、重试/限流/去重、断点续跑、样例断言自检 | 增强：计划持久化（已有）+ 预算阶梯 + 检查点恢复 |
| C5 | 结果校验与交付：交叉验证来源、结构化输出、失败回退方案 | 已有验证/修复轮，补"数据质量断言"技能 |

产品侧改动清单（按优先级）：
1. `workspace_run` 支持受控依赖安装（pip/npm 白名单、超时上限）与更长执行时间；
2. 新增 `web-scraping` 技能（SKILL.md：先探测结构→小样本→批量→校验，记录来源与失败）；
3. 编码类任务的完成校验：回读产物 + 样例断言 + 来源记录；
4. 长任务预算阶梯 + 计划持久化（已落地）；
5. 可选：受控 Playwright 浏览器脚本能力（域名白名单、只读页面、cookie 隔离）。

评测：golden 增加 "coding 信息获取" 旅程（本次已加 J2 骨架）；Terminal-Bench 代码子集 canary；
真实校园网站授权样本人工核对。coding 相关失败进入失败模式库，反哺技能与工具改进。

## 9. 真实评测策略（用户要求，2026-11-19 起生效）

**所有"真实测评"一律通过产品 Agent 代码 + DeepSeek V4 Flash 执行**：真实模型、真实工具执行、真实产物、
官方评分器/真实校验，禁止用 mock 或 harness 捷径冒充真实评测结论。

- **被测对象**：产品 Agent 代码（`agent-loop` + 工具/审批/预算/检查点/验证全链路），冻结快照隔离：
  `eval-freeze-20261119T2015`（sha f069b425，HEAD d5b613f）。
- **模型与配置**：`DeepSeek-V4-Flash`，能力声明 `reasoning_effort`，偏好 `max` 按任务锁定，
  `maxOutputTokens=32768`，单请求超时 360s。
- **真实 canary 集**（固定小样本、可重复、相邻时段对照）：
  1. GDPval public sample 3 题（研究→写作→真实导出）；
  2. HORIZON-001（长程十轮真实产物）；
  3. AppWorld `325d6ec_1`（多步工具/官方评分）；
  4. OfficeBench `1-14/1`（结构化变换/真实文件评分）；
  5. Terminal-Bench 代码子集 8–10 题（可选代码 canary：官方 verifier、docker；单独批次跑）。
- **L2 golden 的 mock 用例只用于确定性机制回归**，结论以 canary + L3 真实体验流（真实后端 API + 真实模型）为准；
- **记录**：`CANARY-REPORT.md`、各阶段日志、`run.summary`/事件日志中的 token/cost/缓存/计划/修复轮指标；
- **对照口径**：架构改动前跑一次基线，改动后同配置重跑；只看"相对基线是否改善 + 失败类型是否减少"。

- **真实 canary 基线（2026-11-19 20:12–21:09，freeze-9，DeepSeek V4 Flash）**：GDPval 1/3、HORIZON-001 探索性通过、AppWorld 325d6ec 失败（1195.6s 撞 1200s 墙）、**OfficeBench 1-14/1 首次通过（196s/5 工具）**。证据：`external-benchmarks/CANARY-REPORT.md`。

- **AppWorld 325d6ec_1 复盘**：1800s 复测 667.7s 完成、4/5 检查通过；唯一失败是动作型任务误带 answer（评测接口契约问题，非能力问题）。已在评测桥对动作型任务移除 answer 并在提示中明确动作/问题区分，重测验证中。
