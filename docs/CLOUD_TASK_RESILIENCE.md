## 问题与最终行为

原任务两次模型和搜索均成功，随后 pg 建连超时被混入任务执行失败。连接池现在在发送 SQL 前对已识别的临时建连错误重试一次；代理默认连接超时 15s，直连 8s，配置上限 30s。默认 query、事务回调和 COMMIT 不自动重放；经审阅并明确接入 readQuery 的任务/事件/检查点/调用、会话/消息、供应商纯读取，中途断线可重试一次。transactionPool 不继承读重试，SQL/认证/证书错误不重试。这不是从任意 SELECT 推断安全性。回滚失败不掩盖原错误，坏连接丢弃；空闲及借出期间均监听连接错误。空闲连接保留 60s 并启用 TCP keepalive。

建连恢复耗尽进入存储中断路径：Postgres 使用单条带 user/worker/attempt/running/lease 条件的 UPDATE 原子暂停，保留已有检查点；条件失效不覆盖新执行者。空闲 Worker 认领连接中断后继续轮询，不重放原认领事务。TLS 证书和主机名验证、凭证加密、owner 与工具授权保持。

重启读回再次捕获已连接后的纯读中断，故补上述显式读恢复。并通过连接器核对原项目区域，依据 [Supabase 官方连接说明](https://supabase.com/docs/guides/database/connecting-to-postgres) 将本机私有配置切到同项目 IPv4 Session Pooler（aws-1-ap-southeast-2、5432），移除数据库 CONNECT 代理。原 CA/密码/服务器主密钥不变；30次顺序读无失败，临时表及行锁验证通过。未改 schema；模型/搜索代理另行保留。这是一次本机观测，不保证网络永不抖动。
